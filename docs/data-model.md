# Data model

PostgreSQL via Drizzle. Schema lives in `packages/db/src/schema/` (one file per area), enums sourced from `@dmtx/schemas`. Migrations in `packages/db/drizzle/`. 31 tables.

## Conventions (every content table)

- **UUIDv7** primary keys (`primaryId()` helper — time-ordered, app-generated).
- `created_at` / `updated_at` (`timestamptz`, auto-`$onUpdate`); `deleted_at` for **soft delete**.
- Editorial `status` enum `draft | published | archived` + `published_at` (not a bare boolean).
- Stable, unique `slug` (freeze after publish).
- `position: integer` for ordering (upgrade path: fractional/LexoRank keys if reorders get heavy).
- Column names are **snake_case** (Drizzle `casing: 'snake_case'`); enums store **English** identifiers, Spanish display lives in the admin dictionary.

## Content building blocks

- **`exercises`** (the atom): name, description, `cues` (jsonb string[]), `difficulty`, `measurement_type` (reps|time|distance), `default_tempo` (jsonb — the 4 phases), `demo_video_asset_id`, `thumbnail_asset_id`, `archived_at` (archived exercises leave the suggestions and the default list; rutinas using them keep working). Joins: `exercise_muscles` (m2m), `exercise_equipment` (m2m).
- **`workouts`** (rutina): three sections — warm-up, main, stretch (`cooldown`) — each **written** (blocks with that `section`), a **video** (`warmup_video_asset_id`, `video_asset_id`, `cooldown_video_asset_id`) or **both** — the app then lets the user follow the class or be guided. `has_video` / `is_guided` (booleans, derived on save from the main section: it has a video class / it has a written rutina) replace the old `type` for lists, catalog filters and analytics; both can be true. `format` is derived too (the main section's first part's, null without a written main section) + `scoring_goal` (jsonb); timing lives on the parts. Video lengths are read from `media_assets`, never stored here. `source_text` holds the rutina exactly as the admin wrote it in the text editor (comments, spacing); the blocks are derived from it on save and the editor reopens the text, not the blocks. `estimated_duration_seconds` is **derived on save** (`sectionValues` in the API: `estimateDurationSeconds` from `@dmtx/core` for the text sections — timers for AMRAP/EMOM/Tabata, a pace heuristic capped by time caps otherwise — per section: the video's length when it has one, else the text's estimate) — never typed by the admin. Structure: `workout_blocks` (type single|superset|circuit|emom|tabata, rounds, rest) → `workout_items` (exercise prescription: sets/reps/`work_seconds`/rest, `tempo_override`, `load_prescription`, `interval_index` for EMOM/Tabata, `per_side`, `goal`).
  - **Parts:** a block of kind `part` carries its own `format` + `format_config` and holds child blocks (`parent_block_id` → the part). A section is a sequence of parts and loose blocks, so "AMRAP 12 min … then 40 burpees … then EMOM 10" is one rutina. The workout-level `format` is the main section's first part's, for lists only.
  - **Principle:** a part's `format_config` = its global timing; blocks/items = the prescription. One structure expresses all formats.
  - **Variants:** a rutina may have variants (RX / Escalada / …) — full `workouts` rows with `variant_of_id` → base and a `variant_label`. Lists and the consumer catalog hide variants; the base's detail returns `variants: [{id, label}]` and the app offers them as a level before starting.
- **`programs`** → `program_days` (ordered; a program is whole weeks, seven days each, week = `position / 7`). Each day is a rest day or **owns** a workout (`program_days.workout_id`; `workouts.owner_program_id` → the program; hidden from every catalog list, deleted with the program) written in the rutina editor — structured text or a single video, like any workout (the app shows it as "Día N"). What it works comes from its days' rutinas (`workout_muscles`), not stored on the program.
- **`skill_progress`** (user × skill, unique): `unlocked_levels` (1 = only the first). Advanced by `POST /api/app/logs`: after a session of a skill level's rutina (the log's `workout_id` is a level's workout), that skill is re-checked: a level passes when **one** session of its own rutina met **all** its goals (per goal, the best set of that session: max reps in a set, max seconds, max distance, max load lifted for at least the goal's reps) — marks from different days or other workouts don't add up; while the current level passes, the next one unlocks. `GET /api/app/skills/:id` returns `unlockedLevels` and, per level, `locked` / `completed` and each goal's `best` and `met`, both from the user's best session of that level (the passing one, else the one meeting the most goals); skill cards carry `progressPct` from it.
- **`skills`** → `skill_levels` (ordered). Each level **owns** a workout (`workouts.owner_skill_id` → the skill; hidden from every catalog list, deleted with the skill) written in the rutina editor, and `unlock_goals` (jsonb `SkillGoal[]`: exercise + metric reps|time_seconds|distance_meters|load_kg + value, derived on save from the level text's **Objetivo** section, one goal per line; the last level has none). What it works comes from its levels' rutinas (`workout_muscles`).

## Shared JSONB value objects (typed by `@dmtx/schemas`)

- **`tempoSchema`** — `{ holdTop, eccentric, holdBottom, concentric }`, each `number | 'X'`.
- **`goalSchema`** — `{ metric, comparator, value, unit? }` (+ `compoundGoalSchema` for AND/OR). Used by `scoring_goal`, item `goal`, and `unlock_goal`. One reusable `meetsGoal()` (in `@dmtx/core`, later).
- **`loadPrescriptionSchema`** — discriminated on `type` (percent_1rm | rpe | absolute | bodyweight).
- **`formatConfigSchema`** — discriminated union on `format`; carries `configVersion` for engine migration.

> **JSONB has no DB-level shape enforcement.** Always validate on write at the API boundary. Add CHECK/trigger for the `type`/`format` discriminant consistency when you build the workouts API.

## Supporting

- **`media_assets`** — single source of truth for every file hosted on Cloudflare: `external_id` is the Cloudflare Images id (kind `image`) or the Stream uid (kind `video`); `name`, `mime_type`, `size_bytes`, `duration_seconds`, `width`/`height` (an image's pixel size is measured in the browser and sent with `POST /api/media/:id/complete`; Cloudflare Images does not report it). No URLs are stored: they are built from the id and the account's delivery codes (`apps/api/src/lib/cloudflare.ts`) — images as `imagedelivery.net/<hash>/<id>/w=…` (flexible variants, so each screen asks for its own size), videos as a signed HLS manifest (the app streams it and the downloads module saves it offline at the quality the user picks; there is no MP4). The one permanent URL is ours: `GET /archivos/:id` on the API (public, view only) serves an image as itself and a video on a bare player page with a fresh token, for «Copiar enlace» in the admin. Content references it by FK. `processing_status` is `uploading` from the moment an upload starts (the record exists before the bytes, so content can reference it right away); an image becomes `ready` when its POST lands; a video goes `processing` while Stream encodes it and `ready` (or `failed`) when Stream says so — polled on `GET /api/media/:id` and the library list, or pushed by the Stream webhook. Only `ready` assets resolve to URLs for the app (`resolveMediaUrls`); `/app/workouts/:id` flags an attached-but-unready video as `videoPending`. Deleting an asset deletes the file at Cloudflare too (storage is billed) and is refused (409) while any exercise, rutina, program, skill or level references it (the row is soft-deleted, so the FKs' `set null` never fires: migration 0041 cleared the references left by deletes from before the refusal existed; saving a rutina drops any section video no longer in the library, and publishing one — or a program — that still points at one is refused with the section, and for a program the week and day); cancelling an upload (`uploading` or `processing`) deletes the row and the file outright.
- **`media_folders`** — nested folders the admin sorts the library into (`parent_id` → self, cascade); `media_assets.folder_id` (set null) files an asset under one; the app never sees folders.
- **`muscles`**, **`equipment`** — the tags an exercise carries. Each muscle belongs to a **zone** (`muscles.zone`, enum `muscle_zone`: chest, back, shoulders, arms, core, legs — fixed, labelled «Pecho», «Espalda», «Hombros», «Brazos», «Core», «Piernas» by `MUSCLE_ZONE_LABEL`; null = «Sin zona», which the app doesn't browse by). A muscle also has `aliases` (jsonb string[]) and a zone has `MUSCLE_ZONE_ALIASES`: other names people search by, never shown. Managed in **Músculos** / **Equipos** or created inline from the exercise form.
- **`workout_muscles`** (workout × muscle, PK both, index `(muscle_id, workout_id)`) — what a rutina works, **stored on save** so browsing is one indexed query: derived from its **main section's** exercises (`manual` false; warm-up and stretch don't count) with `role` `primary` when at least a quarter of those exercises work it, else `secondary` (`deriveMuscles` in `@dmtx/core`), plus the muscles the admin adds by hand in the rutina's Ajustes (`manual` true, primary; `extraMuscleIds` on create/update) — all a video-only rutina has. `workouts.full_body` is set alongside: four zones or more as primary (`FULL_BODY_ZONES`). Re-derived on every save of a rutina (its own, or its program's or skill's), when an exercise's muscles change, and when a muscle changes zone or is deleted (`apps/api/src/lib/workout-muscles.ts`). Migration 0045 backfilled existing rutinas. A program or a skill works what its owned rutinas work.
- **Browsing** — `/app/filters` returns the zones (with their muscles) that published content works, whether any is «Cuerpo completo», and the equipment in use. `/app/browse?zones=arms,back&muscles=biceps&fullBody=1` ranks rutinas, programs and skills by how many of the asked zones/muscles they work (each one criterion; a zone is met by any of its muscles), then by how many primary hits — so «Brazos + Espalda» lists those working both first, then those working one; `fullBody` keeps only content with four primary zones. `equipment`, `video`, `guided` still filter rutinas only. Free text (`q`) ignores accents and case (`unaccent`) and finds content by its name or by what it works: a word of a muscle's or zone's name or alias starting with the text («abdomen» → Core, «isquios» → Femorales). `/app/workouts/:id` → `muscles` are the stored ones, primary first.

## Users & billing

- Better Auth owns `user` / `session` / `account` / `verification` (`packages/db/src/schema/auth.ts`; `user.role` for the admin gate).
- **`profiles`** (1:1), **`subscriptions`** (our own billing record), **`discounts`**, **`payments`** (ledger), **`webhook_events`**. See [billing.md](billing.md).

## Cascade rules

Cascade **down** ownership (workout→blocks→items, program→days, skill→levels; owned workouts cascade from their skill/program). **Never** cascade across content references (skill_level→workout uses `restrict`, program_day→workout `set null`). Media FKs are `set null`.
